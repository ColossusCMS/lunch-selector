# 032 공지 팝업 확장 — `{종류:내용}` 문법·이미지·버튼 모양 (v2.6)

## 지시 (PM)
- 설계서: `docs/design/2026-11-27/notice-rich-content-design.md` (합의 완료). 문법·이미지·안전 원칙·테스트 기준은 설계서 3~7절을 그대로 따른다. 설계서와 이 지시서가 다르면 이 지시서를 따르고 보고에 적는다.
- 회차: 최초.
- 작업 시작 시점: `main` = `f7f2036`. 작업트리에 PM이 쓴 설계서(`docs/design/2026-11-27/`)와 이 지시서가 있다. 기존 테스트 178개.

### 목표
1. 공지 `내용` 칸에 공지 전용 문법을 지원한다. 형태는 `{종류:내용}` 하나로 통일하고, 목록만 줄 맨 앞 `- `를 쓴다.
   - `{굵게:…}`
   - `{빨강:…}` `{파랑:…}` `{초록:…}` `{주황:…}`
   - `{링크:글씨|https://…}`
   - 줄 전체가 `{이미지:파일 이름|설명}`인 이미지 줄(최대 3장)
   - `- ` 목록
2. 이미지는 저장소 `images/notice/<파일 이름>`에서 불러온다. 새 폴더를 만들고 `.gitkeep`으로 유지한다.
3. 하단 버튼(`버튼`·`링크` 칸)은 하나 그대로 두고, 강조색 배경의 버튼 모양 링크로 바꾼다.
4. 운영자용 가이드 `docs/NOTICE-GUIDE.md`를 새로 쓴다(아래 "가이드 문서").
5. v2.6 릴리스 준비: `APP_VERSION = 'v2.6'`, `npm run bump`.

### 하지 말 것
- `README.md`는 고치지 않는다(사용자 결정). 버전 배지도 그대로 둔다.
- `server/`는 고치지 않는다.
- 공지 시트에 칸을 추가하지 않는다. `parseNotices`의 행 유효성 규칙은 바꾸지 않는다.
- `innerHTML`, `insertAdjacentHTML`, `outerHTML`, 시트 값을 넣은 `style` 속성을 쓰지 않는다. 노드 배열을 `createElement`와 `textContent`로만 그린다.
- 별점 카드, 피드백 모달, 공지 표시 순서·숨김 로직은 바꾸지 않는다.
- **실제 구글 폼으로 전송하지 않는다.** 화면 확인 때는 `formResponse` 요청을 가로채 막는다. 운영 시트를 고치지 않는다. 공지 확인은 가짜 CSV로 한다.
- 커밋하지 않는다.

### 구현 메모
- 파서는 `js/notice-markup.js`(신규)에 DOM 없는 순수 함수로 둔다. 예: `parseNoticeMarkup(text)` → 블록 배열
  - 문단: `{type:'paragraph', lines:[[인라인…], …]}`
  - 목록: `{type:'list', items:[[인라인…], …]}`
  - 이미지: `{type:'image', file, alt}`
  - 인라인: `{type:'text', value}`, `{type:'style', style:'bold'|'red'|…, children}`, `{type:'link', text, href}`
  - 이름과 모양은 판단해도 된다. 테스트하기 쉬운 형태면 된다.
- 종류 이름 → 동작은 한 곳의 대응표로 모은다(설계서 9절). 굵게·색 같은 스타일 종류는 "대응표 한 줄 + CSS 클래스 하나 + 테스트"만으로 추가할 수 있어야 한다. 가이드 문서에 이 방법을 적는다.
- `httpsLink`는 `js/notice.js`에서 내보내 재사용한다(동작 변경 없음).
- 이미지 `alt`가 비면 공지 제목을 쓴다. 렌더러가 제목을 받아서 처리한다.
- 이미지 불러오기 실패(`error`)는 그 `<img>`만 지운다.
- 이미지가 길어 팝업이 화면을 넘으면 팝업 안에서 스크롤돼야 한다. 지금 `dialog`의 스크롤 동작을 확인하고, 필요하면 `max-height`와 `overflow-y: auto`를 더한다.
- 색 토큰은 라이트·다크 두 벌이다. 설계서 3.4의 방식을 따르고, 대비비(팝업 배경 대비)를 계산해 보고에 적는다. 목표는 4.5:1 이상이다.
- 기존 `.notice-content { white-space: pre-line }`는 새 구조(문단·목록)에 맞게 정리한다. 문단 안 줄바꿈은 `<br>`로 넣거나 pre-line을 유지한다. 판단은 맡기되, 목록 항목 사이에 엉뚱한 빈 줄이 생기지 않게 한다.

### 가이드 문서 (`docs/NOTICE-GUIDE.md`)
짧고 실용적으로 쓴다. 해요체로 쓴다(사용자에게 보이는 문서다).
1. **공지 작성법(운영자용)**
   - `공지관리` 탭의 칸 설명. `docs/SETUP.md`의 공지 절을 짧게 요약하고 링크한다.

   - 잘못 쓰면 어떻게 보이는지(그 부분만 글자로 남음). 링크 글씨에는 `|`를 쓸 수 없다는 점.

- `docs/SETUP.md`의 공지 절 `내용` 칸 설명에 "문법은 `docs/NOTICE-GUIDE.md`"라는 한 줄 링크를 더한다. SETUP의 다른 부분은 고치지 않는다.

## 수정 지시 1/2 (PM)
리뷰·적대검증 모두 차단 결함 없이 통과했다. 아래 작은 항목만 고친다. 범위 밖 변경은 하지 않는다.

1. **빈 목록 항목** (`js/notice-markup.js`): `- `처럼 하이픈 뒤 내용이 비었거나 공백뿐인 줄이 빈 `<li>`를 만든다. 이런 줄은 목록이 아니라 글 줄로 처리한다("잘못 쓰면 글자로 남는다" 원칙). 테스트를 추가한다.
2. **테스트 보강** (`tests/notice-markup.test.js`): 아래 경계를 추가한다.
   - 설명이 있는 넷째 이미지 줄이 글 줄로 남는다.
   - 짝 없는 `}`가 글자로 남는다(예: `a}b`, `{굵게:a}}`).
   - 1번의 빈 목록 항목.
3. **가이드 보강** (`docs/NOTICE-GUIDE.md`):
   - 앞에 공백을 두고 쓴 `  - 항목`도 목록으로 인식된다는 점을 한 줄 적는다.
   - 해석에 실패한 문법은 그 문법의 여는 괄호부터 닫는 괄호까지 통째로 글자가 된다는 점을 적는다. 이때 안에 든 정상 문법도 함께 글자가 된다. 예: `{링크:{굵게:안내}|http://…}`. 지금 "해당 부분만 글자"라는 표현을 이 동작에 맞게 다듬는다.
   - 개발자용 절에 "문법은 브라우저(`js/notice-markup.js`)에서 해석하므로 추천 서버는 고칠 필요가 없어요"를 명시 문장으로 넣는다.
4. **보고 보강**: 하단 버튼 배경을 `--accent`가 아니라 `--notice-orange`로 한 판단은 유지한다. 흰 글씨 대비 때문이다. 이 판단과 실제 대비비를 완료 보고의 "설계·지시 차이"에 적는다.
