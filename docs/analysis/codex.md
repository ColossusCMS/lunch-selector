# lunch-selector 진단 — 코덱스

## 분석 방법

- 2026-11-02, 약 10분간 정적 검토와 Node 기반 검증을 수행했다.
- 읽은 파일: `AGENTS.md`, 공통 요청서 `docs/analysis/BRIEF.md`, `README.md`, `docs/SETUP.md`, `docs/superpowers/specs/2026-10-19-lunch-selector-design.md`, `docs/superpowers/plans/2026-10-19-lunch-selector.md`, `package.json`, `index.html`, `css/style.css`, `js/`의 9개 모듈, `tests/`의 6개 테스트 파일, `data/sample-stores.csv`.
- `npm test`: **59개 통과, 실패 0개**, 러너 보고 시간 약 124ms. 실행 환경은 `node --version` 기준 v26.12.1. 출력의 `Error: network` 경고 두 건은 실패 후 재시도를 검사하는 테스트의 의도된 로그다.
- `node --input-type=module`로 파일 생성 없이 추가 확인: `cachedLookup`에 `null` 반환 조회를 두 번 요청하면 실제 호출은 1회, 동일 가게 두 행은 함께 추첨됨, 닫히지 않은 CSV 따옴표가 오류 없이 수용됨, 필수 `그룹` 헤더 누락도 정규화 단계에서 통과함.

- 브라우저 화면, 실제 Google Sheets 응답, 실제 Kakao SDK와 외부 서비스 정책·한도는 검증하지 않았다. 관련 항목의 실행 조건과 미확인 범위를 구분했다.
- 기존 소스·테스트는 수정하지 않았으며, 상대 분석 결과는 열람하지 않았다. 작성 파일은 이 보고서 하나다. 과거 구현 계획의 커밋 지시 등은 이번 진단의 실행 지시로 적용하지 않았다.

## 요약

1. **S-01**: 중복 행이 있으면 동일 가게가 여러 순위에 나올 수 있다. 추첨 단위와 가게 식별 기준을 먼저 정할 필요가 있다.
2. **S-02**: 목록 요청에 애플리케이션 차원의 제한 시간이 없어 로딩 상태에서 재시도할 수 없는 구간이 있다.
3. **S-03**: 빠른 모드 왕복 시 모드 객체 비교만으로는 과거 요청을 식별하지 못한다.
4. **S-04**: 일시적인 주소 조회 실패가 `null`로 끝나면 같은 페이지에서 재조회되지 않는다.
5. **E-01 / E-03**: 개인화와 필터 확장은 현재 구조와 잘 맞는다. 여러 사용자가 공유하는 투표·이력·권한은 별도 저장·인증 구조를 결정해야 한다.

## 1. 소스 개선점

### S-01 동일 가게의 중복 행이 추천 확률과 순위를 왜곡한다

- 위치: `js/stores.js:70`, `js/select.js:68`, `tests/select.test.js:66`
- 내용: 추첨은 행 객체를 중복 없이 뽑지만, 같은 실제 가게가 여러 행에 있으면 서로 다른 후보로 취급한다.
- 근거: `rowsToStores([['가게명','그룹'],['A','G'],['A','G']])` 결과를 `pickTop`에 전달하면 `['A','A']`가 나온다. 기존 테스트의 `new Set(r).size`는 객체 참조의 중복만 검사한다. 설계의 “같은 가게 중복 추천 금지”는 시트가 가게당 한 행이라는 전제에 의존한다.
- 영향: 같은 곳이 1·2순위에 나오거나, 중복 등록한 가게의 당첨 확률이 올라간다. 여러 그룹을 각각 행으로 등록하는 실수가 특히 취약하다.
- 제안: 우선 중복 경고를 제공한다. 식별 열 `id`를 도입하거나 이름·주소 조합으로 중복 후보를 감지하고, 그룹 병합 또는 입력 오류 처리 정책을 정한다. 이름만으로 자동 병합하면 동명 지점을 합칠 수 있으므로 피한다. 중복 행과 동명 지점 테스트를 추가한다.
- 확신도: 높음 — Node에서 재현.
- 규모: M(반나절)

### S-02 목록 요청이 지연되면 사용자가 재시도할 수 없다

- 위치: `js/data.js:14`, `js/app.js:281`
- 내용: `fetch`와 본문 읽기에 명시적인 제한 시간이나 취소 처리가 없다.
- 근거: `load()`는 시작 시 돌리기를 비활성화하고 재시도 버튼을 숨긴다. 요청이 resolve/reject되지 않는 동안 이 상태가 계속된다. 현재 테스트는 즉시 성공하거나 즉시 실패하는 fetch만 다룬다.
- 영향: 느리거나 응답이 끝나지 않는 연결에서 “불러오는 중...”에 머문다. 브라우저 자체의 네트워크 종료 시간에 복구를 맡기게 된다.
- 제안: `AbortController`로 요청·본문 처리의 제한 시간을 설정하고, 제한 시간 초과를 재시도 가능한 오류로 표시한다. 모드 변경 시 불필요한 이전 요청을 취소하는 정책도 함께 정한다. 지연 요청과 취소 후 상태 복구를 검증한다.
- 확신도: 높음 — 제한 시간 부재와 UI 흐름을 코드로 확인, 실제 네트워크 지연은 미재현.
- 규모: M(반나절)

### S-03 모드 객체 비교로는 같은 모드의 오래된 요청을 배제하지 못한다

- 위치: `js/app.js:263`, `js/app.js:281`, `js/app.js:296`
- 내용: 결과 적용 여부를 `mode !== state.mode`로 검사하므로 요청 자체의 최신성은 보장하지 않는다.
- 근거: 최초 점심 요청 A가 진행 중일 때 카페→점심으로 왕복하면 새 점심 요청 C가 시작된다. `MODES`의 같은 객체가 다시 사용되므로 A와 C 모두 현재 모드 검사에 통과한다. C 성공 후 A가 늦게 성공하면 결과·필터를 다시 초기화할 수 있고, A가 늦게 실패하면 정상 화면에 실패 문구를 띄울 수 있다. 로딩 중 모드 버튼은 계속 사용할 수 있다.
- 영향: 빠른 왕복이나 재시도에서 화면이 뒤늦게 초기화되거나 성공·실패 표시가 어긋날 수 있다.
- 제안: `load()`마다 증가하는 요청 번호를 두고 최신 번호만 상태를 변경하게 한다. 또는 모드별 진행 중 Promise를 공유하되, 화면 반영에는 별도의 요청 번호를 쓴다. A→B→A 순서와 성공·실패 완료 순서를 바꾼 테스트가 필요하다.
- 확신도: 높음 — 제어 흐름 확인, 브라우저 재현은 미실시.
- 규모: M(반나절)

### S-04 주소 조회의 null 결과가 영구 캐시된다

- 위치: `js/map.js:25`, `js/map.js:84`, `js/map.js:91`, `tests/map.test.js:39`
- 내용: 주석은 실패를 캐시하지 않는다고 하지만 실제로는 reject만 제거하고, `null`로 resolve된 결과는 유지한다.
- 근거: `cachedLookup(async () => { calls++; return null; })`를 같은 주소로 두 번 호출하면 `calls === 1`. 실제 `search`는 OK가 아닌 응답을 모두 `null`로 바꾼다. 기존 실패 재시도 테스트는 throw하는 조회만 검사한다.
- 영향: 일시 오류와 실제 검색 결과 없음이 구분되지 않고, 같은 페이지에서 다시 돌려도 해당 주소 핀이 복구되지 않을 수 있다.
- 제안: 최소한 `null` 결과를 캐시에서 제거한다. 검색 결과 없음과 일시 장애를 구별할 수 있으면 짧은 만료 시간과 오류별 재시도 정책을 둔다. 동시 요청 공유는 유지하고 null 재조회 테스트를 추가한다.
- 확신도: 높음 — Node에서 재현.
- 규모: S(1시간 이내)

### S-05 데이터 오류가 “시트에 가게가 없어요”로 뭉뚱그려진다

- 위치: `js/stores.js:62`, `js/stores.js:83`, `js/app.js:299`, `js/csv.js:24`
- 내용: 필수 `그룹` 헤더 누락, 전체 미사용, 그룹 없는 행만 존재, 실제 빈 시트를 같은 UI로 처리한다. CSV 구문 오류도 일부 조용히 수용한다.
- 근거: 필수 헤더 검사는 `가게명`에만 있고, UI는 `listGroups(...).length === 0`으로 빈 시트를 판단한다. `parseCsv('가게명,그룹\n"A,G')`는 오류 없이 `[['가게명','그룹'],['A,G']]`를 반환한다. 정상 Sheets 내보내기가 이런 CSV를 만든다는 뜻은 아니며, 대체 데이터와 수동 편집에 대한 방어 공백이다.
- 영향: 운영자가 원인을 찾기 어렵다. 일부 잘못된 행은 업종·휴무 등 의도와 다른 기본값으로 처리될 수 있다.
- 제안: 필수 헤더와 중복 헤더를 검사하고, 정규화 결과와 행 번호를 포함한 진단 목록을 분리해 반환한다. 전체 미사용·누락 그룹·빈 목록의 안내를 구분한다. CSV 따옴표 미종결은 명시적으로 오류 처리하되, 허용할 입력 범위는 기존 관대한 정책과 맞춘다.
- 확신도: 높음 — 헤더 누락과 미종결 따옴표는 Node에서 확인.
- 규모: M(반나절)

### S-06 비동기 안내와 순위 링크의 접근성을 보완할 수 있다

- 위치: `index.html:50`, `index.html:52`, `js/app.js:89`, `js/app.js:195`, `css/style.css:275`
- 내용: 최종 결과용 live region은 있지만 로딩·실패·후보 없음 메시지는 자동 안내 대상이 아니다. 2·3순위 카드는 릴 시작 전에 `hidden=false`가 되고, 표시 전에는 opacity만 0이다.
- 근거: `#message`에는 `role=status`나 `aria-live`가 없다. `fillRank()`는 링크를 먼저 생성하고 `revealInOrder()`가 나중에 `.show`를 붙인다. opacity는 요소의 포커스 가능 여부를 제어하지 않는다. 링크 이름도 모두 “📍 카카오맵”이다.
- 영향: 화면 낭독기 사용자가 상태 변경을 놓칠 수 있고, 키보드 사용자는 연출 중 눈에 보이지 않는 순위 링크에 도달할 수 있다. 링크 목록에서 가게를 구분하기도 어렵다.
- 제안: 메시지에 적절한 상태 안내를 적용하고, 공개 전 카드는 `hidden` 또는 `inert`로 제어한다. 링크 접근 가능한 이름에 가게명·순위를 포함한다. 키보드 순서와 화면 낭독기 실제 동작을 확인한다.
- 확신도: 높음 — DOM/CSS 확인, 보조 기술 실측은 미실시.
- 규모: M(반나절)

### S-07 다크 테마의 강조색 위 흰 글자는 대비가 낮다

- 위치: `css/style.css:21`, `css/style.css:33`, `css/style.css:121`, `css/style.css:161`
- 내용: 다크 테마의 강조색 `#ff8a3d` 배경에 버튼과 선택 칩의 `#fff` 글자가 놓인다.
- 근거: Node에서 sRGB 상대 휘도로 계산한 대비는 약 2.35:1이다. 라이트 강조색 `#e8590c`와 흰색 조합도 약 3.58:1이다. 밝은 주황색을 배경·글자 공통 토큰으로 쓰면서 생기는 문제다. 실제 화면 렌더링은 확인하지 않았다.
- 영향: 작은 선택 칩과 버튼 문구가 특히 읽기 어렵다.
- 제안: 강조 배경 위 글자용 토큰을 별도로 두고 다크 테마에서는 어두운 글자를 검토한다. 라이트 버튼 배경도 더 어둡게 조정하는 등, 실제 글자 크기에 맞춰 대비를 검증한다. 핀 색상도 함께 확인한다.
- 확신도: 높음 — 선언된 색상 조합 기준.
- 규모: S(1시간 이내)

### S-08 동작을 조립하는 계층의 자동 검증이 비어 있다

- 위치: `tests/map.test.js:1`, `tests/theme.test.js:1`, `js/app.js:190`, `js/app.js:281`
- 내용: 순수 함수 테스트는 충실하지만 `app.js`, 애니메이션, SDK 로딩·지도 표시, DOM 테마 적용을 직접 검증하지 않는다.
- 근거: 현재 테스트는 파싱·정규화·선택·URL 생성·조회 캐시·테마 값 파싱에 집중한다. S-03의 요청 경쟁, S-06의 공개 시점, SDK 실패 후 추천 유지 같은 조립 동작은 59개 통과만으로 보장되지 않는다.
- 영향: 모듈 내부는 정상이어도 사용자 흐름에서 회귀가 생길 수 있다.
- 제안: 우선 모드 요청 경쟁, 연타 방지, 후보 0·1·2곳, 지도 실패 후 추천 유지의 소수 시나리오를 검증한다. 요청 번호와 상태 전이를 DOM 밖으로 분리하면 Node 테스트를 유지할 수 있다. 실제 브라우저 검증은 키보드·모바일·모션 감소에 집중한다. 테스트 수를 늘리기 위한 단순 DOM 복제 테스트는 피한다.
- 확신도: 높음
- 규모: M(반나절), 브라우저 자동화 체계까지 추가하면 L(하루 이상)

### S-09 사용자가 입력한 문자열의 안전한 출력 방식을 유지해야 한다

- 위치: `js/app.js:64`, `js/app.js:94`, `js/map.js:14`, `js/map.js:124`
- 내용: 검토한 출력 경로에서는 시트 문자열을 `textContent`와 텍스트 노드로 넣고, 검색 링크 이름은 URL 인코딩한다. 직접적인 시트 내용 기반 HTML 삽입 문제는 발견하지 않았다.
- 근거: 결과 카드와 지도 오버레이 모두 문자열을 `innerHTML`로 결합하지 않는다. 링크 호스트도 코드에 고정되어 있다. 공개 편집 허용은 설계에서 수용한 정책이며, 이를 새 취약점으로 분류하지 않는다.
- 영향: 향후 강조 표시·메모 링크·검색 기능에서 HTML 문자열 결합으로 바꾸면 현재의 안전한 경계가 사라질 수 있다.
- 제안: 이 출력 규칙을 유지하고 `<img ...>` 같은 문자열이 실행되지 않고 텍스트로 표시되는 검증을 주요 출력 경로에 둔다. 사용자 입력 URL을 추가한다면 허용 프로토콜을 검사한다. 실제 공유 권한과 도메인 제한은 코드만으로 확인할 수 없다.
- 확신도: 높음 — 검토한 소스 경로에 한정.
- 규모: S(1시간 이내), 현재 즉시 수정할 결함은 확인하지 못함.

## 2. 확장 가능성

### E-01 필터와 개인화는 현재 모듈 구조 안에서 확장하기 좋다

- 위치: `js/stores.js:8`, `js/select.js:40`, `js/app.js:36`
- 내용: 가격대·도보 시간·인원 수·좌석·메뉴 제약 등은 시트 열과 정규화 모델, 순수 후보 필터를 늘려 구현할 수 있다.
- 근거: 데이터 정규화와 추천 로직이 DOM에서 분리되어 있으며, 필터는 매번 후보 배열을 생성한다. 즐겨찾기·최근 방문은 기존 저장소 접근 방식을 확장할 수 있다.
- 영향: 백엔드 없이 실사용 편의를 높일 수 있다. 조건과 칩이 늘면 480px 화면과 `app.js`의 이벤트 관리가 먼저 복잡해진다.
- 제안: 가격·시간은 문자열 비교 대신 명시적 숫자·범위로 정규화한다. 후보 수를 먼저 보여주고 고급 필터는 접어서 제공한다. 방문 이력 등은 안정적인 가게 ID를 도입한 뒤 저장한다.
- 확신도: 높음 — 구조 적합성 판단이며 실제 사용자 수요는 별도 확인 필요.
- 규모: M(반나절)부터, 필터 종류와 UI 수에 따라 L(하루 이상)

### E-02 모드 추가는 간단하지만 조직별 독립 설정에는 경계가 있다

- 위치: `js/config.js:18`, `js/config.js:39`, `js/app.js:10`, `js/app.js:351`, `css/style.css:61`
- 내용: 동일 시트의 탭 추가는 자연스럽다. 조직·사무실별 별도 시트, 많은 모드, 모드별 선호 그룹에는 추가 설계가 필요하다.
- 근거: 게시 URL과 시트 ID가 전역 하나이고 그룹 저장 키도 모드 공통이다. 모드 0개면 `selectMode(undefined)`가 호출되어 `mode.id` 접근에서 초기화가 실패한다. 모드 버튼 컨테이너는 줄바꿈 설정이 없다.
- 영향: 단순 점심·카페를 넘어가면 설정 복제, 그룹 선택 덮어쓰기, 좁은 화면의 가로 넘침이 생길 수 있다. 현재 2개 모드에서 화면 넘침을 재현했다는 뜻은 아니다.
- 제안: 설정 로딩 시 모드 0개·중복 ID를 검사한다. 모드마다 데이터 출처를 선택할 수 있게 하고, 선호 그룹은 모드별로 저장한다. 모드 수가 늘면 선택 UI를 변경한다.
- 확신도: 높음
- 규모: M(반나절)

### E-03 공유되는 상태와 권한은 읽기 전용 CSV의 범위를 넘는다

- 위치: `js/data.js:14`, `js/config.js:47`, `js/app.js:53`
- 내용: 공통 목록을 읽는 기능과 기기 내 개인화는 가능하다. 팀 투표, 공동 방문 이력, 계정별 권한, 조작을 방지하는 공정 추첨 기록은 현 데이터 경로만으로 완성할 수 없다.
- 근거: 앱의 원격 통신은 CSV 읽기와 지도 조회이며 공유 결과를 저장하거나 사용자 신원을 검증하는 경로가 없다. localStorage는 브라우저별 저장소다.
- 영향: “모두에게 같은 결과”나 “동료가 남긴 표가 즉시 보임”을 보장하려면 저장·동시성·인증을 담당할 별도 서비스가 필요하다.
- 제안: 정적 구성을 유지할 때는 결과·필터를 URL에 담아 전달하거나 외부 설문으로 연결한다. 공동 쓰기가 필수라면 관리형 저장소나 별도 API 도입을 별도 범위로 결정한다. 쓰기 자격 증명을 정적 JS에 넣는 방식은 사용하지 않는다.
- 확신도: 높음
- 규모: URL 공유 M(반나절), 인증·공동 쓰기 L(하루 이상)

### E-04 데이터 규모보다 전체 다운로드·화면·조회 정책이 먼저 제약이 된다

- 위치: `js/data.js:17`, `js/select.js:20`, `js/select.js:68`, `js/app.js:195`
- 내용: 현재는 모드 전체 CSV를 메모리에 읽고, 그룹·업종 칩을 모두 렌더링한다. 후보 필터와 셔플은 후보 수에 비례한다. 지도 조회는 추첨 결과 최대 3개에 한정되어 있어 유리하다.
- 근거: 파싱·정규화·필터·셔플이 전량 처리이고 `Promise.all`은 뽑힌 가게만 조회한다. 지오코딩 캐시는 페이지 메모리 안에 있어 다른 사용자의 조회나 새로고침에는 공유되지 않는다.
- 영향: 규모가 커지면 네트워크·파싱과 수많은 필터 버튼, 반복 지오코딩이 부담이 된다. 성능 측정 없이 특정 행 수나 동시 사용자 수를 한계로 단정할 수 없다.
- 제안: 실제 대량 CSV로 로드 시간·입력 반응성을 먼저 측정한다. 목록 검색과 필터 축약을 적용하고, 주소 좌표 열을 도입해 검증된 좌표를 재사용할 수 있다. 서비스 한도는 운영 시 별도로 확인해야 한다.
- 확신도: 높음 — 처리 구조 판단, 처리량 상한은 미측정.
- 규모: 측정·UI 정리 M(반나절), 좌표 운영 체계 L(하루 이상)

### E-05 최신성·오프라인 요구는 캐시 정책을 명시해야 한다

- 위치: `js/app.js:50`, `js/app.js:288`, `js/app.js:305`
- 내용: 성공한 목록은 페이지를 닫거나 새로고침하기 전까지 모드별로 재사용한다. 새로고침 없는 시트 반영이나 오프라인 재방문은 현재 제공하지 않는다.
- 근거: `storeCache`에는 만료나 무효화 경로가 없고, 메모리 캐시 외에 최근 정상 목록 저장이 없다. 이는 현재 문서의 새로고침 안내와 일치하므로 그 자체를 버그로 분류하지 않는다.
- 영향: 상시 열어놓는 용도로 바꾸면 목록이 오래될 수 있다. 오프라인 캐시를 추가하면 오래된 휴무 정보로 추천할 위험도 함께 생긴다.
- 제안: 마지막 성공 조회 시각, 명시적인 목록 새로고침, 캐시 만료를 먼저 도입한다. 오프라인 지원은 앱 파일과 최근 정상 데이터의 보관 정책을 나누고, 캐시 데이터 사용 중임을 표시한다. 게시 원본 자체의 반영 지연을 앱 캐시 삭제만으로 없앨 수는 없다.
- 확신도: 높음
- 규모: 새로고침·시각 표시 M(반나절), 오프라인 지원 L(하루 이상)

## 3. 추가 기능 후보

아래는 제안이며 구현하지 않았다. 방문 이력·복잡한 휴무·투표 등 기존 설계의 비목표에 해당하는 항목은 목표 변경을 먼저 확인해야 한다.

### F-01 오늘의 후보 목록과 제외 이유 보기

- 사용 장면: 돌리기 전 “한식이 몇 군데 남았는지”, “왜 이 가게가 안 나오는지” 확인하고 싶은 동료.
- 구현 개요: `filterCandidates` 결과 수와 목록을 접이식으로 표시한다. 휴무·미사용·그룹·업종 제외 사유는 별도 순수 함수로 계산한다.
- 현 구조와의 궁합: 매우 좋음. 기존 데이터를 그대로 활용하며 S-05의 운영 진단에도 도움이 된다.
- 확신도: 높음
- 규모: M(반나절)

### F-02 이번에는 이 가게 빼고 다시 뽑기

- 사용 장면: 세 후보 모두 최근에 갔거나, 현장에 가 보니 쉬는 가게를 이번 선택에서만 제외하려는 그룹.
- 구현 개요: 현재 세션의 제외 ID 집합을 필터에 추가하고 “제외 해제”를 제공한다. 전체 목록의 사용여부는 건드리지 않는다. 후보 0개가 되면 제외 조건을 안내한다.
- 현 구조와의 궁합: 좋음. 공유 데이터 쓰기가 필요 없고 정기휴무 외의 상황을 즉시 반영할 수 있다. 안정적인 가게 ID가 선행되면 좋다.
- 확신도: 높음
- 규모: M(반나절)

### F-03 동료에게 결과와 선택 조건 공유

- 사용 장면: 먼저 돌린 사람이 메신저로 1·2·3순위와 지도 링크를 전달하는 경우.
- 구현 개요: 먼저 텍스트 복사를 제공하고, 필요하면 모드·그룹·업종·결과 ID·추첨 날짜를 URL에 담는다. 수신 시 삭제된 가게나 오래된 결과를 구분한다.
- 현 구조와의 궁합: 좋음. 백엔드 없이 가능하지만 공유 URL은 합의된 기록이나 조작 방지 증명이 아니다. 필터만 공유하는 것과 결과까지 공유하는 것을 명확히 구분해야 한다.
- 확신도: 높음
- 규모: 텍스트 복사 S(1시간 이내), 결과 URL M(반나절)

### F-04 예산·이동 시간·인원 조건으로 후보 좁히기

- 사용 장면: 점심시간이 짧거나, 여러 명이 함께 이동하거나, 팀별 예산이 정해진 날.
- 구현 개요: 가격 범위·도보 분·권장 인원 등의 시트 열을 추가한다. 값 없는 가게를 포함할지 사용자가 이해할 수 있는 정책을 둔다.
- 현 구조와의 궁합: 좋음. 실시간 길찾기 대신 관리자가 적은 도보 시간을 쓰면 현재 구조를 유지할 수 있다. 데이터 관리 부담이 생긴다.
- 확신도: 중간 — 입력 유지 가능성과 실제 수요 확인 필요.
- 규모: L(하루 이상)

### F-05 기기 내 방문 이력과 최근 방문 제외

- 사용 장면: 같은 팀이 같은 브라우저로 반복 사용하며 지난 며칠 간 곳을 피하고 싶은 경우.
- 구현 개요: “여기로 갔어요”를 눌렀을 때만 ID·날짜를 저장하고, 최근 N일 제외를 선택 기능으로 제공한다. 추첨된 것을 방문한 것으로 자동 기록하지 않는다.
- 현 구조와의 궁합: 개인·공용 기기 기준으로 좋음. 기기 간 동기화나 팀 전체의 공통 이력은 제공되지 않는다. 원 설계에서 명시적으로 제외했던 기능이므로 요구 변경 확인이 선행되어야 한다.
- 확신도: 중간
- 규모: M(반나절)

### F-06 기간이 있는 임시 휴무

- 사용 장면: 관리자가 연휴·휴가·공사 기간을 미리 알아서 목록에 반영할 때.
- 구현 개요: 휴무 시작일·종료일을 선택 열로 두고 정규화 단계에서 날짜를 검증한다. 기한이 지나면 자동으로 다시 후보에 넣고 제외 이유를 표시한다.
- 현 구조와의 궁합: 정적 CSV와 잘 맞는다. 실제 영업 여부를 자동 확인하는 기능은 아니다. 복잡한 반복 규칙까지 확장하기 전에 단순 날짜 구간부터 검토한다. 기존 비목표 변경에 해당한다.
- 확신도: 중간
- 규모: M(반나절), 복수 구간·예외 규칙까지 포함하면 L(하루 이상)

## 판단 보류 · 질문

- 같은 가게의 기준은 무엇인가? 동명 지점을 구분해야 하는지, 가게당 하나의 안정적인 ID를 시트에 추가할 수 있는지에 따라 S-01과 이력·공유 설계가 달라진다.
- 사용 패턴이 매번 새로 여는 방식인지, 회사 PC에 계속 켜 두는 방식인지 확인하면 E-05의 우선순위를 정할 수 있다.
- 그룹 선호는 점심·카페가 공유해야 하는가, 각 모드가 따로 기억해야 하는가? 현재는 하나의 그룹 저장 키를 공유한다.
- 공동 편집 허용은 기존 설계의 명시적 선택이다. 현 운영에서도 같은 정책인지, 게시 데이터의 공개 범위와 실제 편집 권한이 어떻게 설정되어 있는지는 확인하지 않았다. 소스만 보고 권한 설정이 잘못됐다고 판단하지 않는다.
- 원 설계는 브라우저 로컬 요일을 의도적으로 선택했다. 해외 접속과 한국 영업일 기준이 필요해지기 전에는 이를 버그로 보지 않는다.
- 실제 모바일 배치·긴 메모·키보드 탐색·화면 낭독기·지도 지연/실패 경로는 브라우저에서 추가 확인이 필요하다. 이 보고서의 테스트 통과 수는 그 검증을 포함하지 않는다.
- 기능 우선순위는 F-01→F-02→F-03을 제안한다. 방문 이력·임시 휴무·공동 투표는 기존 비목표와 운영 부담을 함께 검토한 뒤 결정한다.
