# lunch-selector 진단 요청서 (공통)

클로드와 코덱스가 **같은 요청서를 받아 따로** 분석한다. 결과를 나란히 비교해 각자의 강점을 확인하는 것이 목적이다.

## 규칙

- **소스 수정 금지.** `js/`, `css/`, `index.html`, `tests/`, `data/` 등 기존 파일은 읽기만 한다. 쓰는 파일은 자기 결과 파일 하나뿐이다.
- **상대 결과 파일을 읽지 않는다.** 둘 다 끝날 때까지 `docs/analysis/` 안의 다른 결과 파일은 열지 않는다.
- git commit / push 하지 않는다 (커밋은 사용자가 직접 한다).
- 테스트 실행(`npm test`)·로컬 실행 등 **읽기성 검증은 해도 된다.** 했다면 결과에 적는다.
- 한국어로 쓴다. 코드·식별자·파일명은 원문 그대로.

## 결과 파일

- 클로드: `docs/analysis/claude.md`
- 코덱스: `docs/analysis/codex.md`

## 분석 범위 (세 갈래)

1. **소스 개선점** — 버그 가능성, 엣지 케이스, 구조·중복, 테스트 빈틈, 접근성, 성능, 보안(XSS 등), 유지보수성
2. **확장 가능성** — 현재 구조(구글 시트 게시 CSV, ES 모듈 분리, 백엔드·빌드 없음)를 유지한 채 어디까지 늘릴 수 있는지, 어디서 막히는지
3. **추가 기능 후보** — 실제 사용 장면(회사 점심·카페 고르기, 층별 그룹)에서 나올 만한 기능

배경 자료: `README.md`, `docs/SETUP.md`, `docs/superpowers/specs/`, `docs/superpowers/plans/`

## 출력 양식

```markdown

## 요약
가장 중요하다고 보는 항목 5개 이내 (ID로 참조)

## 1. 소스 개선점

- 내용: 무엇이 문제인지
- 근거: 그렇게 판단한 이유 (코드 인용, 재현 조건 등)
- 영향: 사용자/유지보수에 미치는 영향
- 제안: 어떻게 고치면 되는지
- 확신도: 높음 | 중간 | 낮음
- 규모: S(1시간 이내) | M(반나절) | L(하루 이상)

## 2. 확장 가능성
### E-01 ... (같은 항목 구성, 위치는 해당 시 기재)

## 3. 추가 기능 후보
### F-01 ...
- 사용 장면: 누가 언제 이걸 원하나
- 구현 개요 / 현 구조와의 궁합 / 확신도 / 규모

## 판단 보류 · 질문
사용자에게 확인이 필요한 것
```
